# 2026-10-31 | 생성 속도 개선 — fp16 (PR #13)

## Problem

AnyDoor 생성이 한 장에 53~303초로 느리고, 같은 조건에서도 시간이 크게 흔들렸다(같은 A3 조건 6회 53~245초).
사용자 판단: VMD가 상품 여러 장을 바꿔 보려면 이 속도로는 비효율적이다(10/29).

## Context

- D21(10/27)에서 "기능 완성 먼저, fp16은 그 이후"로 정했고, 오전에는 "회의 전날 품질이 바뀌면 시연이 흔들린다"는 이유로 fp16을 회의 뒤로 미루자고 Claude가 제안했다
- 사용자가 "속도 개선 지금 안 되나?"라고 물어, **기본값을 바꾸지 않는 실험 사본으로 먼저 확인**하는 조건으로 진행했다
- 오전 시간 편차 조사에서 공유 메모리·클럭 제한·온도·다른 프로그램은 원인이 아니었고, 전용 메모리가 매번 9.7~10GB/10GB로 한계에 붙어 있었다([품질 실험 기록 §6](2026-10-31_quality-experiments.md))

## 원인 분석 (Claude, 코드 확인)

- 체크포인트(4.9GB, 반정밀도 저장)를 fp32로 올리면 약 9.8GB → 10GB GPU에 다 올라가지 않는다
- 그래서 `save_memory`가 **생성할 때마다** UNet·ControlNet과 DINOv2·VAE를 CPU↔GPU로 옮겼다(`low_vram_shift`). 이 이동이 느리고, 실행마다 걸리는 시간이 달랐던 것으로 보인다
- fp16으로 바꾸면 약 4.9GB → 모델 전체가 GPU에 계속 올라가 있어 옮길 필요가 없다

## Implementation

| 변경 | 내용 |
| --- | --- |
| `model.half()` | 가중치를 반정밀도로 (`VMD_FP16=1`, 기본값) |
| `torch.autocast(float16)` | 조건 계산 → 샘플링 → 디코딩 구간 |
| `save_memory` | fp16이면 끔 (CPU↔GPU 이동, sliced attention 사용 안 함) |
| 되돌리기 | `VMD_FP16=0`으로 실행하면 기존 방식(fp32 + save_memory) |
| 확인용 | `/health`에 `precision`, 응답 헤더 `X-Precision` |

AnyDoor 원본 코드는 고치지 않았다. 먼저 저장소 밖 실험 폴더에 사본을 만들어 확인한 뒤 저장소에 반영했다.

## Result (학교 PC, seed 42, 오늘 품질 실험과 같은 입력)

| 조건 | fp32 (기존) | fp16 |
| --- | --- | --- |
| A3 페이스아웃 | 195.6초 (같은 조건 6회 53~245초) | **10.2 / 9.0 / 9.3초** |
| A4 마네킹 | 297.4초 | **9.1초** |
| 결과 차이 | 기준 | 픽셀 평균 차 0.02~0.03 — 눈으로 구분 안 됨 |
| 같은 조건 반복 | 최대 픽셀 차 1 | 최대 픽셀 차 3~5 |

- **약 20배 빨라졌고 시간 편차도 사라졌다(9~10초).** 오전의 "메모리 한계 근처 동작" 가설과 맞는 결과
- 품질 실험 결론(D24)과 시연 조건은 그대로 유효
- **실제 서비스 화면 확인 (사용자)**: Spring에서 [Preview 생성] → 페이스아웃 약 10초, 마네킹 약 11초. 사용자 반응: "wow"

## Decision

- D25: AI 서버를 **fp16 기본값**으로 전환, `VMD_FP16=0`으로 기존 방식 유지 (사용자 요청 → AI가 원인 분석·실험 사본으로 검증 → 사용자 확인 후 병합)
- 화면 생성 안내: "보통 1~4분" → "보통 30초 이내"
