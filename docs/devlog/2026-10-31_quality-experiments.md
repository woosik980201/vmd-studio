## 2. A1 — 영역 비율 (H1, 10/29)

가설: AnyDoor가 상품 윤곽 힌트를 **영역 사각형 크기로 늘리기 때문에**(10/27 코드 분석) 좁고 긴 영역에서 원피스가 된다.
같은 행거 사진·같은 빨간 정면 누끼 티, 영역의 **높이(h)만** 줄임.

- **결과**: 결과 티는 세 번 모두 **영역 사각형을 거의 그대로 채웠다.** 영역 비율을 줄이면 원피스 → 반팔 티로 단계적으로 바뀌었고, A1b는 원본 비율과 거의 같다 → H1을 수치로 뒷받침

## 4. VMD 관점의 재해석과 범위 결정 (10/29)

실험 결과를 본 뒤 사용자가 VMD 실무 관점에서 두 가지 문제를 제기했다.

- **Problem 1** — 매장 행거는 대부분 **옆으로 걸린** 진열인데, 본사 상품 사진은 대부분 **정면**이다. VMD는 정면 사진을 넣을 가능성이 크다
- **Problem 2** — 상품 하나 교체에 2~4분은 비효율적이다. 실제 VMD 업무 단위는 상품 1개가 아니라 행거 한 줄·벽면 하나라서 **여러 상품 교체**가 필요하다

**AI 활용 (Claude)** — 선택지와 판단 근거 정리

| Problem 1 선택지 | 판단 |
| --- | --- |
| A. 옆으로 건 사진을 요구 | 본사 사진이 대부분 정면이라 부담 큼 → 보조 안내로만 |
| B. 정면 → 옆 변환 모델 추가 | 범위 확대, 품질 보장 없음 → MVP 밖 |
| **C. 적용 위치를 나눔** | 정면 사진과 진열 방향이 같은 자리(페이스아웃·마네킹 등)에 우선 적용 |
| D. 사이드 행잉은 "색·배치 확인용"으로 기대치 조정 | 옆 행잉에서 VMD가 보는 건 컬러 순서·길이 리듬 |

- Problem 2는 **두 문제**로 나눔: ① 대기 시간 — 여러 장 기능을 만들어도 상품마다 생성하므로 시간은 줄지 않음(5벌 = 10~20분), 생성 시간 편차 원인을 먼저 확인 ② 업무 단위 요구 — 맞는 요구지만 D18(10/12)에서 "AnyDoor 실험 후 판단"으로 보류한 항목. 연쇄 생성(결과를 다음 입력으로)은 주변 변화가 누적될 위험
- 범위 후보 비교: 정면 행잉(페이스아웃) — 사진·진열 방향이 같아 가장 유리 / 마네킹 — 정면이지만 옷이 몸에 입혀진 "피팅" 문제라 불확실(9/28 PoC #03B 팔 환각) / 스타일링 — 여러 상품 교체 문제가 다시 생기고, "어떤 코디가 좋은가"로 가면 AI가 판단하는 구조가 되어 D2와 충돌

**User Decision (사용자)** — "원했던 기능은 너무 큰 욕심이었을 수도 있다"며 **VMD Studio의 활용 범위를 좁히는 방향**을 채택. 여러 상품 교체는 다음 단계로 둔다. 어디까지 포함할지는 A3(페이스아웃)·A4(마네킹) 실험 결과를 보고 정하기로 함

### 5-2. 마네킹 추가 검증 (10/31)

| --- | --- | --- | --- | --- |
| 2 | 한 팔 주머니 | 약 70% (가까이) | 42 · 1 | **0/2** — 팔이 사람 피부색으로 바뀜 |

- **관찰**: 마네킹 4의 seed 1은 팔이 흰색으로 유지됐지만, 주머니에 넣은 손이 티 밑단에 가려져 팔이 곧게 내린 것처럼 보인다. 배경에 사각형 경계가 약하게 보인다
- **해석 (Claude, 추정)**: 가까이 찍으면 영역이 커지고 영역 주변에 남는 "흰 마네킹" 단서가 적어, AnyDoor가 영역 안의 팔을 사람 팔로 다시 그리는 것으로 보인다
- **마네킹 종합**: 마네킹 전체가 나오게 찍은 사진(1·3·4)은 **8/8 통과**, 가까이 찍은 사진(2)만 0/2 실패. 사전 기준(전체 80%)으로는 10회 중 8회(80%)이고 실패 2회가 모두 같은 조건이다 → 범위에 넣는다면 **입력 조건(구도)을 함께 정해야 한다**

## 6. 생성 시간 편차 (10/31)

**Problem** — 같은 설정인데 생성 시간이 39.5초 ~ 303.6초로 다름. 10/27에 본 "연속 생성 시 공유 GPU 메모리 증가"가 원인이라는 가설을 확인.

**방법** — A3 → A4 → A3 → A3를 연속 실행하며 Windows 성능 카운터로 **전용·공유 GPU 메모리**, nvidia-smi로 **GPU 사용률**을 2초 간격 기록.

| 실행 | 생성 시간 | 공유 메모리 평균 | 전용 메모리 평균 | GPU 사용률 (중앙값) |
| --- | --- | --- | --- | --- |
| A3 r1 (서버 켠 직후) | 195.6초 | 0.75GB | 9.64GB | 100% |
| A4 | 297.4초 | 0.82GB | 9.54GB | 100% |
| A3 r2 | **89.2초** | 0.68GB | 9.46GB | 100% |
| A3 r3 | 217.3초 | 0.75GB | 9.50GB | 100% |

- **결과**: **같은 조건(A3)이 89초 ~ 217초로 2.4배 차이**나는데, 공유 메모리·전용 메모리·사용률은 거의 같다
- **결론**: "공유 메모리로 넘쳐서 느려진다", "연속 실행할수록 느려진다"는 이번 데이터로는 **뒷받침되지 않음**(r2가 가장 빠름). `save_memory` 적용 후에는 공유 메모리가 0.7~0.9GB 수준에서 안정적이다
- 다음 가설: GPU 클럭·전력 제한(스로틀) 또는 다른 프로그램의 GPU 사용 → 2차 확인(아래)

### 6-2. 2차 확인 — 클럭·전력·온도·다른 프로그램

같은 A3 조건 3회를 다시 실행하며 nvidia-smi로 클럭·전력·온도·**클럭 제한 원인**, Windows 성능 카운터로 **프로세스별 GPU 사용률**을 2초 간격 기록.

| 실행 | 생성 시간 | SM 클럭 평균 | 전력 평균 | 온도 | 클럭 제한 |
| --- | --- | --- | --- | --- | --- |
| T1 | 128.0초 | 1946MHz | 144W | 46~58℃ | 없음 |
| T2 | 245.3초 | 1946MHz | 141W | 55~59℃ | 없음 |
| T3 | **53.4초** | 1930MHz | **167W** | 55~61℃ | 없음 |

- **배제한 원인**: 클럭 제한(전력·온도 스로틀 기록 없음), 과열, 다른 프로그램의 GPU 사용(AI 서버 외 프로세스 합계 0.3% 이하), 연속 실행 누적(오늘 7회 중 가장 빠른 두 번이 3·7번째)
- **남은 단서**: 사용률이 100% 가까운데 전력은 320W 중 140W대로 낮다. GPU가 계산보다 **메모리를 기다리는 시간**이 길다는 신호일 수 있다. 생성 중 전용 메모리는 매번 9.7~10.0GB / 10GB로 한계에 붙어 있다
- **새 가설 (Claude, 검증 전)**: 메모리가 한계에 가까우면 PyTorch가 메모리를 확보하려고 캐시를 비우고 다시 할당하는 일이 실행마다 다르게 일어나, 같은 조건에서도 시간이 크게 달라질 수 있다. 확인하려면 AI 서버 로그에 단계별 시간과 PyTorch의 할당 재시도 횟수(`num_alloc_retries`)를 남겨야 한다(코드 변경 필요)
- **의미**: 편차는 무작위에 가깝고 회차가 쌓여 생기는 문제가 아니다. 메모리 사용량을 줄이는 **fp16 작업(11/3~4 계획)이 속도와 편차를 함께 줄일 가능성**이 있다

오늘 같은 조건 A3의 생성 시간 6회(r1~r3, T1~T3): 195.6 / 89.2 / 217.3 / 128.0 / 245.3 / 53.4초 → **53~245초**. 화면 안내는 "1~4분 소요"가 정확하다.
